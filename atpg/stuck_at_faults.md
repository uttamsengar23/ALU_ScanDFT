# Stuck-at Fault Model

## What is a stuck-at fault?

A **stuck-at fault** models a common class of manufacturing defect: a
signal (a wire, a gate output, a flip-flop output) that is permanently
fixed at a logic value — either **0** (stuck-at-0) or **1**
(stuck-at-1) — regardless of what it should actually be driving based
on the design's intended logic.

In a real chip, this can happen from causes like a short to ground
(stuck-at-0), a short to the supply rail (stuck-at-1), an open circuit
that floats to a fixed value, or a bridging defect between adjacent
nets. It's the most widely used fault model in digital test because a
large fraction of real silicon defects behave this way electrically,
even though the physical cause can vary.

## Why test for it?

Functional simulation (like `alu_tb.sv` in this project) proves the
**design** is correct — that the RTL implements the intended
behavior. It says nothing about whether a specific **manufactured
chip** came out correctly. A chip can pass every functional test in
simulation and still contain a physical defect on real silicon, because
simulation never touches actual hardware.

Manufacturing test exists to catch that gap: apply patterns to a real,
fabricated chip and check whether its outputs match what a
known-good (fault-free) chip would produce. If a stuck-at fault is
present, *some* pattern should expose it by producing a different
output than the golden result.

## Fault sites modeled in this project

For `ALU_DFT`, the fault sites chosen are the 4 bits of the ALU's
registered `result` output:

| Site        | Description                    |
|-------------|---------------------------------|
| `result[0]` | LSB of the ALU's result register |
| `result[1]` | bit 1                           |
| `result[2]` | bit 2                           |
| `result[3]` | MSB of the ALU's result register |

Each site is modeled with **both** stuck-at values, giving **8 total
modeled faults**:

- `result[0]` stuck-at-0, `result[0]` stuck-at-1
- `result[1]` stuck-at-0, `result[1]` stuck-at-1
- `result[2]` stuck-at-0, `result[2]` stuck-at-1
- `result[3]` stuck-at-0, `result[3]` stuck-at-1

**Why the result bits specifically:** they are the ALU's primary
observable output, so they're the most direct place to demonstrate the
detect/miss concept without needing internal scan access for this
particular check (the scan chain itself is exercised separately, in
`scan_tb.sv`, to prove internal state is *also* controllable/observable
— see `dft_datasheet.md` for how the two pieces fit together).

## How detection works here

For each modeled fault, every pattern in the test set
(`test_patterns.txt`) is applied to both:

1. The **golden** ALU logic (fault-free, correct behavior)
2. A **faulty** version, where the chosen bit is forced to its stuck
   value after the real result is computed

If the golden and faulty outputs differ for *any* pattern in the set,
that fault is marked **DETECTED** — the test set is capable of
exposing that specific defect. If no pattern in the set produces a
difference, the fault is marked **MISSED** — a blind spot in the test
set for that defect.

## Result

All 8 modeled faults were detected by the 10-pattern test set —
**100% fault coverage** for this fault model. See
`fault_results.log` / `fault_coverage.py`'s report for the full
per-fault breakdown, and `fault_tb.sv` for the implementation.

## Scope and limitations

This is a student-scoped demonstration of the *concept*, not a
replacement for real ATPG tooling:

- Only `result[3:0]` bits are modeled as fault sites here — a real
  ATPG flow would also model faults on internal gates, the `zero`/
  `carry`/`negative` flag logic, and the scan chain's own flops.
- Test patterns were hand-picked to give good coverage across
  opcodes and corner cases, not automatically generated by an ATPG
  algorithm (which would search for the *minimum* pattern set needed
  for maximum coverage — genuinely complex commercial tooling territory).
- No bridging faults, transition faults, or other more advanced fault
  models are covered — stuck-at is the simplest and most foundational
  model, which is why it's the right starting point for a first DFT
  project.
